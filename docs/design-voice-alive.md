# 设计：语音交互 + 「还在吗」（v1）

> 状态：设计稿，未实现。
> 本轮范围：语音交互（系统识别 + 拼音容错）、「还在吗」本地检测 + 短信预警。
> 遥控子女端：本轮只留接口边界，下一轮做（见第 5 节）。
> 前提：`minSdk 24`、`targetSdk 34`、Kotlin + ViewBinding，无 Compose。

---

## 1. 语音交互

### 1.1 老人看到什么

主页新增一个内置色块 `HomeAction.VOICE`，标签「说话」，颜色用 `accent` 系（区别于现有 10 个）。

点开 → `VoiceActivity`（全屏、深色底）：

```
┌─────────────────────────────┐
│         请说话              │  ← 大字，跟字号设置
│                             │
│           ◯◯◯              │  ← 160dp 圆形麦克风，说话时脉冲
│                             │
│      正在听…                │
│    「打电话给儿则」          │  ← 实时 partial 结果，28sp
│                             │
│           [取消]            │
└─────────────────────────────┘
```

**为什么显示实时识别文字**：老人看到自己说的话被识别成什么，才有反馈感；不显示的话，他不知道机器到底听没听见。识别错了也能自己重说。

**为什么不按「按住说话」**：老人手抖，按住时中途松手就断。改成**点一下开始，说完自动停**（静音 1.2 秒判停），再点一下也可以立即结束。

### 1.2 识别链路

```
色块 → VoiceActivity
  ├─ 检查 RECORD_AUDIO（首次运行时请求；拒绝则提示去设置开）
  ├─ SpeechRecognizer.isRecognitionAvailable()
  │    └─ false → 明确提示「这台手机没有语音识别服务」
  ├─ Intent(RecognizerIntent.ACTION_RECOGNIZE_SPEECH)
  │    ├─ EXTRA_LANGUAGE_MODEL   = FREE_FORM
  │    ├─ EXTRA_LANGUAGE         = Locale.getDefault()（zh-CN）
  │    ├─ EXTRA_PARTIAL_RESULTS  = true
  │    ├─ EXTRA_MAX_RESULTS      = 3      ← 多个候选逐个匹配，命中率显著提升
  │    └─ EXTRA_SPEECH_INPUT_COMPLETE_SILENCE_LENGTH_MILLIS = 1200
  ├─ 最长录音 8 秒（命令都是短句，避免卡住）
  └─ onResults → VoiceCommandMatcher.match(candidates)
       ├─ 命中 → 执行 + TTS 复述 + finish()
       └─ 未命中 → 「没听清，再说一次」+ 显示识别原文
```

**多候选为什么重要**：系统识别会给出多个结果，正确的说法常常排在第 2、3 位。只在第 1 位匹配等于浪费一半机会。

**引擎可用性**：国产 ROM 有些需要在「设置 → 语音输入」里选引擎，没选时 `isRecognitionAvailable()` 直接 false。这种情况必须明确告知，不能静默失败——这是这类功能的通病。

### 1.3 命令集（封闭，15 条）

不做自由对话。命令越少，容错越狠。

| 命令 | 标准说法（任一命中） | 动作 |
|---|---|---|
| 打电话（无名） | 打电话、我要打电话、拨号 | 打开 `DialActivity` |
| 打电话给 X | 打电话给儿子 / 给儿子打电话 / 打给儿子 | 见 1.5 |
| 打开 X | 打开微信 / 开抖音 / 我要看视频 | 见 1.5 |
| 收音机 | 收音机、开收音机、听广播、听收音机 | `RadioLauncher`（见 1.6） |
| 报时 | 几点了、现在几点、报时、什么时间 | TTS 播当前时间 |
| 手电筒 | 手电筒、开灯、照亮、太黑了 | `TorchManager.on()` |
| 音量 | 声音大点 / 小点、太吵了 | `AudioManager` 调一格 |
| 字大点 | 字太小、看不清楚、字大一点 | `FontSizeManager` 升一级 |
| 视频号 | 视频号、看视频号 | `ActionExecutor.openChannels()` |
| 回桌面 | 回桌面、回家、退出 | `finish()` |
| 还要吗/在不在 | 「你还在吗」 | TTS 回应（测试语音链路是否通） |

> 「救命」**不在这个表里**，单独处理，见 1.7。

### 1.4 拼音容错算法（核心）

`PinyinMatcher`——这是整套方案能用的前提。

**问题**：老人说方言或口齿不清，系统识别出来往往是同音错字。
- 「打电话」→「打电发」
- 「收音机」→「收银机」
- 「手电筒」→「手电同」

**做法**：不比较汉字，比较**拼音**。

1. **汉字转拼音**：引入 `com.github.promeg:tinypinyin:2.0.3`（约 100KB，纯 Java，Android 专用，比 pinyin4j 小且没有 GBK 坑）。
2. **命令词侧**：每条标准说法的拼音**预先算好并手工校对**。这样多音字（「行」「重」「还」）在命令侧永远准确，不受库的多音字能力影响。
3. **识别结果侧**：实时用 tinypinyin 转全拼。
4. **归一化**（模糊音，只做声母/韵母级替换）：

   | 混淆组 | 规则 |
   |---|---|
   | 平翘舌 | `zh→z`、`ch→c`、`sh→s` |
   | 前后鼻音 | `ing→in`、`eng→en`、`ang→an` |
   | 鼻音边音 | `n→l`（仅声母位） |
   | 儿化/尾音 | 去掉结尾的 `r` |

5. **打分**（取最高）：
   - 原文包含标准说法 → **1.0**
   - 归一化拼音完全相等 → **0.95**
   - `1 - levenshtein(拼音A, 拼音B) / max(len)` → 0~1
   - 首字母串相等（`dhgez` vs `dhgez`）→ **0.6**（短促说法的兜底）
6. **阈值 0.62**，低于视为未命中。阈值抽成常量 `MATCH_THRESHOLD`，方便真机调。

**为什么不做语音识别微调或大模型**：命令集只有 15 条，且都是短句。拼音距离在这个规模下的准确率已经足够，而且是离线的、零成本、零延迟。大模型在这里是杀鸡用牛刀，还引入联网依赖。

### 1.5 参数化命令

两类，走同一个 `resolveTarget()`。

**A. 打电话给 X**

```
提取「打电话给」「给…打电话」「打给」之后的部分 → 候选人名
  ↓
在三个来源里按拼音匹配（复用 PinyinMatcher，阈值放宽到 0.55，因为人名同音字多）
  1. 快捷拨号（QuickContact）—— 优先，因为老人自己配过
  2. 紧急联系人（SOS）
  3. 通讯录（READ_CONTACTS 已有权限）
  ↓
唯一命中 → TTS「正在打给儿子」→ 拨号
多个命中 → 列候选（头像 + 名字 + 号码大按钮），让老人点
无命中   → TTS「没找到这个人，请说通讯录里的名字」
```

通讯录遍历要缓存：首次加载到内存 `List<ContactEntry(name, pinyin, phone)>`，子线程构建，之后纯内存匹配。几千条也就几十毫秒。

**B. 打开 X**

```
提取「打开」「开」「我要」之后的部分
  ↓
先查内置功能关键词表（收音机 / 手电 / 视频号 / 微信 / 抖音 / 设置）
  ↓ 未命中
再查已安装应用（QUERY_ALL_PACKAGES 已有）：按应用标签的拼音匹配
  ↓ 未命中
TTS「没找到这个应用」
```

顺序不能反：先内置再 App，否则「打开收音机」会被某个网络电台 App 抢走。

### 1.6 收音机探测（`RadioLauncher`）

**这里有硬件层面的现实**：2020 年后的手机大多取消了 FM 芯片，系统里根本没有收音机 App。所以只能尽力探测，不能承诺成功。

探测顺序：
1. 已知包名：`com.android.fmradio`、`com.huawei.android.fmradio`、`com.miui.fm`、`com.oppo.fmradio`、`com.vivo.fm`、`com.samsung.android.fmm`
2. Intent：`android.intent.action.FM`、`android.intent.action.RADIO`（部分 ROM 私有）
3. 全量扫：`queryIntentActivities` 里标签含「收音机 / FM / Radio」的
4. 全失败 → TTS「这台手机没有收音机」+ 弹一句说明（不静默）

### 1.7 安全边界：「救命」必须二次确认

SOS 会**发短信 + 打电话给紧急联系人**。语音识别误判的代价太大：电视里演一句、家人聊天提一句「吓死我了救命」，都会触发。

规则：

```
识别到「救命 / 救救我 / 快来救我 / 我不舒服」
  → 不执行 SOS
  → 弹全屏红色确认页，3 秒倒计时自动执行
  → 老人点「我没事」或说「取消」→ 撤销
```

倒计时 3 秒是刻意的：老人真出事时喊完就没力气再操作，所以要用**默认执行**；但留 3 秒给误触发留退路。这个取舍要写死在代码注释里，别以后被人「优化」成直接执行。

### 1.8 失败与降级

| 情况 | 表现 |
|---|---|
| 没有 `RECORD_AUDIO` | 提示并跳应用权限页 |
| 没有可用识别引擎 | 明确说明「这台手机没有语音识别服务」，附一句怎么去设置里选引擎 |
| 识别需要联网但断网 | 「语音识别需要联网，请检查网络」 |
| 识别超时（8 秒） | 「没听清，再说一次」 |
| 匹配不上 | 显示识别原文（小字），让老人/家属看出是「没听见」还是「听错了」 |
| 命令执行失败（如没装微信） | 复用现有 `Toast` 文案，不新增 |

**复述必须做**：执行成功一律 TTS 回一句「正在打给儿子」。老人不看屏幕，光有动作他不知道有没有生效。

```

res/layout/activity_voice.xml
```

## 2. 「还在吗」

### 2.1 为什么不能照搬「死了么」

「死了么」是**主动签到**：每天点一下。老人不会做这件事，三天后就形同虚设。

改成**被动检测**：只要今天碰过手机，就算「还在」。老人不需要做任何事。

### 2.2 数据

PrefsManager 新增：

| key | 类型 | 说明 |
|---|---|---|
| `alive_enabled` | Boolean | 默认 **false**（要家属主动开） |
| `alive_last_active` | Long | 最后一次解锁时间 |
| `alive_last_alert` | Long | 上次发预警的时间 |
| `alive_alert_count` | Int | 本轮已发条数（最多 3） |
| `alive_pause_until` | Long | 暂停到什么时候 |
| `alive_threshold_hours` | Int | 阈值，12 / 24 / 48，默认 24 |
| `alive_notify_phone` | String | 预警接收号，空则回落 SOS 号码 |

### 2.3 活跃采集（`AliveCenter.touch()`）

三个来源，取最新，写 Prefs 时节流（同一分钟内只写一次，避免频繁 I/O）：

1. **`ACTION_USER_PRESENT`（解锁）** —— 主信号。动态注册（Android 8+ 静态注册无效），注册在 `ElderAccessibilityService` 里（它常驻）。
2. **无障碍的 `TYPE_WINDOW_STATE_CHANGED`** —— 每次窗口变化也算活跃，天然覆盖「正在用手机」。
3. **App 前台 `onResume`** —— 兜底。

**为什么不用亮屏（`SCREEN_ON`）**：半夜摸黑看一眼时间是亮屏但不算「在用」。解锁才是真信号。

### 2.4 定时检查（`AliveAlarmReceiver`）

**这里是整个功能最容易做虚的地方**：`WorkManager` 在 Doze 下会被推迟几小时到一天，「24 小时预警」实际可能 30 小时才发。必须用 `AlarmManager`：

```
setExactAndAllowWhileIdle(RTC_WAKEUP, now + 1h, pendingIntent)
```

- **间隔 1 小时**（不是 30 分钟）：24 小时的阈值，1 小时精度完全够，还省电。
- **Android 12+ 要精确闹钟权限**：`canScheduleExactAlarms()` 为 false 时降级 `setAndAllowWhileIdle`（不精确但能跑），并在高级设置里显示状态。
- **一次性闹钟要自己续**：触发后重新排下一次。
- **开机恢复**：已有 `BootReceiver`，在里面重排。

### 2.5 判定与发送

```
每次触发：
  if (!enabled) return
  if (now < pauseUntil) return
  idle = now - lastActive
  if (idle < thresholdHours * 3600_000) { alertCount = 0; return }   ← 恢复活跃就清零
  if (alertCount >= 3) return                                        ← 最多 3 条
  if (alertCount > 0 && now - lastAlert < 12h) return                ← 二次提醒间隔 12h
  → 发短信，lastAlert = now, alertCount++
```

**恢复通知**：从「已报警」状态回到活跃时，发一条「已恢复操作」短信，然后清零。这个细节很重要——子女收到预警后会一直担心，得有个明确的结束信号。

### 2.6 短信文案

首次（`alertCount == 0`）：
```
【长辈助手】提醒：家里手机已有 26 小时没有操作
（上次活跃：10月25日 14:30）。
如无异常请忽略；若联系不上，请尽快打电话确认。
```

后续：
```
【长辈助手】仍未检测到手机操作，已持续 38 小时。
```

恢复：
```
【长辈助手】已恢复：家里手机刚刚有操作，此前提醒解除。
```

### 2.7 暂停

高级设置里「暂停提醒」→ 1 天 / 3 天 / 7 天 / 取消暂停。

**为什么必须有**：住院、出远门、手机落家里都会误报。连续误报几次，子女就不信这个提醒了，功能等于失效。误报抑制比报警灵敏度更重要。

### 2.8 边界情况

| 情况 | 行为 | 是否需要处理 |
|---|---|---|
| 首次开启功能 | `lastActive` 初始化为当前时间 | 必须，否则一开就报警 |
| 重装 / 换机 | 同上，从当前时间起算 | 天然正确 |
| 手机没电关机 | 闹钟不跑，开机后 `BootReceiver` 重排，首次检查立即发现超时 → 报警 | 符合预期（关机 2 天子女确实该知道） |
| 老人一直不动但手机在充电 | 照常报警 | 正确 |
| 阈值内恢复活跃 | 清零 `alertCount`，不发恢复短信（因为没报过） | 正确 |
| 未开 `SEND_SMS` | 报警失败，本地 Toast 提示家属去开权限 | 需处理 |
| 未设预警号码 | 回落 SOS 号码；都没有则不启用并提示 | 需处理 |

### 2.9 不做什么

- **不在主页显示**「你 20 小时没动手机」—— 只会让老人焦虑，这功能是给子女的。
- **不采集位置**（除了 SOS 那条既有逻辑）—— 省电、少隐私负担。
- **不做云端上报**—— 留给下一轮（见第 5 节）。

### 2.10 新增文件

```
util/AliveCenter.kt              活跃时间读写、判定、暂停
receiver/AliveAlarmReceiver.kt   定时检查 + 发短信 + 续排闹钟
res/layout/activity_admin.xml    加「还在吗」卡片（原有文件，改）
```
改动：`ElderAccessibilityService` 注册 `USER_PRESENT` + 上报活跃；`BootReceiver` 重排闹钟；`AdminActivity` 加开关/阈值/暂停/诊断显示。

## 4. 实施顺序

1. **拼音层**（`PinyinMatcher`）—— 独立、可单元测试，先做。这一步错了后面全错。
2. **语音页 + 识别**（`VoiceActivity`）—— 先只支持「报时」，把链路跑通。
3. **命令集 + 参数化命令** —— 逐条加，每加一条真机试一次。
4. **收音机 / 救命确认页** —— 依赖 1~3 成立。
5. **「还在吗」数据层 + 闹钟** —— 与语音无依赖，可并行。
6. **短信 + 高级设置 UI**。

每步都 `assembleDebug` 通过 0 error / 0 warning 再往下走。

## 5. 验收标准

**语音**
- 安静室内，普通话正常语速，10 句话至少 8 句正确执行
- 故意说错字（「打电发」「收银机」）仍能命中
- 说「救命」弹确认页，不点则在 3 秒后才执行
- 手机没装微信时说「打开微信」，提示清楚且不崩

**还在吗**
- 阈值设 12 小时，把 `alive_last_active` 手动改到 13 小时前，等下一次闹钟（或手动触发）→ 收到短信
- 改回当前时间 → 不再报，且收到「已恢复」短信
- 暂停 3 天后，超时不发
- 重启手机后，闹钟仍然有效

## 6. 遥控子女端：本轮不实现，只留边界

下一轮要加的东西（**本轮不写任何代码**，只是确认现在的设计不会挡路）：

| 需要 | 现在的状态 | 是否已预留 |
|---|---|---|
| 心跳数据源 | `AliveCenter.lastActiveAt` | 天然可用 |
| 配置序列化 | `PrefsManager` 全是 key-value + JSON（`HomeBlock.listToJson` 等） | 天然可用 |
| 设备标识 | 无 | **缺**，下一轮首次启动生成 UUID |
| 绑定关系 | 无 | **缺**，下一轮做一次性绑定码 |
| 变更审计 | 无 | **缺**，下一轮记「谁在什么时候改了什么」 |

下一轮的三个已知硬约束，先记在这里，免得以后低估：

1. **推送是死结**。国内 Android 后台限制，想「立刻收到」只能走厂商推送通道，需要企业资质。个人项目的现实做法是**心跳拉取**，延迟 15–30 分钟——对改字号、加快捷拨号这种低频操作完全够。
2. **子女端做微信小程序**，扫码绑定，不用装 App，开发量远小于双端原生。
3. **远程改配置 = 远程控制别人的手机**。绑定码一次性且限时，危险操作（改紧急联系人、关闭 SOS）在老人端必须有可见提示。这条不能因为「反正是家里人」而省掉。
