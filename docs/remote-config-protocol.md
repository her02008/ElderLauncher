# 远程配置协议 v1.1

> 状态：已实现（Workers + NAS 两套服务端 + Android 客户端）。
> 这份文档是**契约**：改协议先改这里，两边实现再跟着改。

---

## 1. 目标与非目标

**目标**：子女能远程帮长辈改桌面配置、看长辈手机状态。**同一套协议，服务端可以换**——
今天跑在 Cloudflare Workers（免费、可达性有保证），明天搬回自家 NAS + `cloudflared`，长辈端一行代码不用改。

**非目标**：

- 不做秒级实时控制。配置下发是低频操作，15–60 分钟延迟完全够。
- 不做远程同屏、远程点击。那是另一类产品，信任和合规都过不去。
- **不做账号体系**。`code` 既是长辈手机的绑定凭证，也是子女的访问凭证。
  一个 `code` 对应一台长辈手机；一个子女可以在浏览器里存多个 `code`（管多位长辈），
  多个子女也可以共用一个 `code`（一起管一位长辈）。细节见 §6.1。

**核心取舍**：**服务在哪里，和协议长什么样，是两件事。** 所以长辈端只认「地址 + 协议」，
不关心对面是 Worker 还是客厅里那台旧笔记本。换服务只需要在老人端改一次地址，历史配置不受影响
（配置本来就存在老人端本地，服务端只是投递箱）。

## 2. 角色

```
子女 ──浏览器/手机──▶ 服务端（Workers 或 NAS）  ◀──HTTP── 长辈手机（长辈助手 App）
                        ▲
                        └── 只存「待执行指令」和「最近状态」，不存完整配置
```

**服务端不保存长辈的完整配置**，只保存：

- 一条绑定的 token
- 待执行指令队列（执行完即可删）
- 最近一次回执上报的状态快照

这样即便服务端被人看到，拿不到家里完整的桌面布局和通讯录。

## 3. 常量

| 名称 | 说明 |
|---|---|
| `endpoint` | 服务根地址，如 `https://elder.example.com`，**不带结尾斜杠** |
| `code` | 家庭标识，6–12 位 `[A-Z0-9]`，同时是绑定凭据。部署时由你设定 |
| `deviceId` | 长辈端首次启动生成的 UUID，存在本地 |
| `token` | 首次 `bind` 时服务端下发，32 位 hex，之后所有请求用它签名 |
| `rev` | 指令修订号，单调递增整数。客户端靠它判断"有没有新东西" |

**`code` 就是全部凭据，别外传**。它出现在 URL 路径里，所以务必走 HTTPS。

---

## 4. 鉴权

绑定之后每个请求带三个头：

```
X-Device: <deviceId>
X-Ts:     <unix 秒>
X-Sig:    <hex( HMAC-SHA256( token, METHOD \n PATH \n TS \n BODY ) )>
```

- `PATH` 含查询串，如 `/b/8F2C3D1E/cfg?rev=12`
- `BODY` 是原始请求体；GET 用空串
- 服务端校验 `|now - X-Ts| <= 300` 秒，防重放
- 常量时间比较签名，别用 `==`

**为什么在 HTTPS 之上还加签名**：token 可能被日志、代理、手机备份带出去。签名让"泄露的 token"
只能重放 5 分钟内的请求，且必须配合同样泄露的 deviceId。成本只是十几行 HMAC。

`bind` 本身不签名（此时还没有 token），靠 `code` 保密 + HTTPS 保护。

## 5. 设备端接口

### 5.1 绑定

```
POST /b/{code}/bind
Content-Type: application/json

{ "deviceId": "…", "name": "妈的手机", "model": "HUAWEI P40", "version": "1.0.26" }
```

返回：

```json
{ "ok": true, "token": "…", "rev": 0, "serverTime": 1730000000000 }
```

- 同一个 `code` 重复 bind 会**轮换 token**（旧 token 立刻失效）。这是"换手机"和"怀疑泄露就重绑"的入口。
- 已绑定的 `code` 被陌生 deviceId 绑走，会让原手机失联——所以 `code` 泄露的代价是"别人能顶掉你"。
  文档里必须写明；真要更强，下一版加 `pairKey`（绑定专用短口令，用一次即废）。

### 5.2 拉取指令

```
GET /b/{code}/cfg?rev={客户端当前 rev}
```

返回：

```json
{
  "rev": 190234567,
  "serverTime": 1730000000000,
  "cmds": [
    { "id": "c_7f3a9b1c2d", "op": "set_font", "args": { "level": 2 }, "at": 1730000000000 }
  ]
}
```

- 客户端 `rev` 与服务端一致 → `cmds` 返回空数组（省一次队列读取）。
- **`cmds` 永远是「全部未回执的指令」**，不是「新增的」。客户端按 `id` 去重。
- **`rev` 是 32 位安全的小整数**：`秒级时间戳 - 1600000000`，当前约 1.9 亿。
  **不要把毫秒时间戳直接当 `rev`**——长辈端用 `JSONObject.optInt` 解析，1.7e12 会被
  截断成负数，客户端就永远认为版本变了，每次同步都重跑一遍历史指令。
- `rev` 只做「有没有变化」的提示，**不承担正确性**。它只增不减；多个子女同时下发时
  可能拿到同一个值，此时两条指令都在 `cmds` 里，客户端一次就能拉全。
- **指令是幂等的**。重发、重复执行都不会更糟：`set_font` 就是设成某个值，不是"加一级"。
- 即使这样，长辈端仍保留一层兜底：**回执队列里已有的 `id` 不重复执行**。
  这挡住了「执行成功但回执丢了、服务端下次又发一遍」的情况。

### 5.3 回执

```
POST /b/{code}/ack
Content-Type: application/json

{
  "rev": 12,
  "results": [ { "id": "c_7f3a", "ok": true, "error": "" } ],
  "state": {
    "lastActive": 1730000000000,
    "alive": "on",
    "fontLevel": 2,
    "voice": true,
    "version": "1.0.26",
    "battery": 78,
    "pending": 1
  }
}
```

`state` 全部字段可选，服务端只做整体覆盖保存，供子女端页面展示。`pending` = 还在等老人确认的危险指令条数。

## 6. 管理端接口（子女用）

`admin.html` 是唯一的界面，两个服务端都原样提供。

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/a/{code}` | 控制台页面 |
| GET | `/a/{code}/api/state` | 绑定信息 + 最近状态 + 待执行指令 |
| POST | `/a/{code}/api/cmd` | `{op, args}` 追加一条指令 |
| POST | `/a/{code}/api/clear` | 清空未执行指令 |

### 6.1 多设备与多成员

v1.1 明确支持两种"多"，都不需要账号体系：

**一个子女管多个长辈** —— 一台手机一个 `code`，服务端彼此独立。
`admin.html` 用浏览器本地存储维护设备清单（`localStorage['elder_devices']`，
形如 `[{id, name, alias, reportedName, endpoint, code}]`），顶部可切换。
**清单只存在子女自己的浏览器里**，服务端不知道谁管几台。换浏览器 / 换手机要重新加一次。

清单里每台设备的**主键是 `id`（浏览器生成的 `d_xxxxxx`），不是 `code`**。
原因：家庭码只在**同一个服务端内**唯一。你既管着 Workers 上的妈妈（码 `8888`）、
又管着自家 NAS 上的丈母娘（码也是 `8888`），是完全可能的；拿 `code` 当主键，
后加的一台会把前一台的地址覆盖掉。判重仍然用「地址 + 码」，切换 / 删除走 `id`。

**多个子女管同一个长辈** —— 把同一个 `https://地址/a/{code}` 发给几个人即可。
服务端不做身份区分，**看到的是同一份队列**：A 发的指令 B 也能看到，
ack 之后一起消失，所以不会重复发。

这带来三个已写明的代价：

1. **没有审计**：指令只记录 `op` / `args` / `at`，不知道是谁发的。
2. **无法单独撤销某个子女**：想让某人失去权限只能换 `code`，
   代价是所有子女的链接失效、长辈手机重绑。
3. **共享的是同一把钥匙**：拿到 `code` 的人既能绑手机也能下指令。

要做「谁能改、谁只能看」，需要引入 `member:{code}:{mid}`（名字 + 口令 hash + 角色）
并把指令带上 `by`。这是 v2 的事，`member:` 是纯新增键，不会返工。

管理端**只靠 `code` 鉴权**（和绑定同一把钥匙）。这是 v1 的简化，写进文档免得误解：
知道 `code` 的人既能绑手机也能下指令。

## 7. 指令集（白名单，封闭）

服务端**只允许**下发这些 `op`。长辈端遇到未知 `op` 直接回 `ok:false, error:"unknown op"`，
不执行、不猜测。**永远不下发可执行代码或任意 Intent。**

| op | args | 危险 | 说明 |
|---|---|---|---|
| `set_font` | `{level:0\|1\|2}` | 否 | 字号：标准 / 大 / 超大 |
| `set_voice` | `{on:bool}` | 否 | 语音播报开关 |
| `set_alive` | `{on:bool, hours:12\|24\|48}` | 否 | 「还在吗」超时预警 |
| `set_home_order` | `{order:["sos","grid","quick"]}` | 否 | 三大区域上下顺序 |
| `push_msg` | `{text:"…", seconds:8}` | 否 | 在长辈桌面弹一条大字提示（子女留言） |
| `set_sos` | `{name:"…", phone:"…"}` | **是** | 紧急联系人 |
| `set_blocks` | `{blocks:[…]}` | **是** | 整份主页色块（结构同 `HomeBlock.listToJson`） |
| `set_quick` | `{contacts:[…]}` | **是** | 整份快捷拨号（结构同 `QuickContact.listToJson`） |

### 危险指令为什么必须本机确认

远程改紧急联系人 = 等于能让"救命"打到某个陌生号码上；远程改快捷拨号 = 等于能让老人一点就拨给别人。
这两类**不能静默生效**，否则这个功能就变成了"家庭成员之间的远程控制通道"。

规则：

1. 危险指令不执行，进 `remote_pending`，等老人回到桌面时弹确认。
2. 老人点「同意」才执行；点「不同意」立刻作废。
3. **超过 24 小时未处理自动作废**，回执里报 `ok:false, error:"expired"`。
4. 老人端弹窗必须写清楚「这是 XX 发来的」，且不可远程关掉。

## 8. 失败与降级

| 情况 | 长辈端行为 |
|---|---|
| 没配网络 | 静默跳过，不弹任何东西（老人不该被网络问题打扰） |
| HTTP 非 2xx | 记 `lastError`，下次闹钟重试 |
| 签名错（401） | 记 `lastError = "auth"`，高级设置里显示「绑定已失效，请重新绑定」，不自动重绑 |
| 服务端不可达 | 静默，保持本地配置不变 |
| 未知 op | 回执 `unknown op`，继续处理下一条 |
| 指令执行中异常 | 回执 `ok:false` + 异常信息摘要，**不影响其它指令** |

**一条指令失败不能中断整批**，这是回执数组存在的理由。

## 9. 服务端存储模型

两套实现用同样的键：

| 键 | 值 |
|---|---|
| `bind:{code}` | `{token, deviceId, name, model, version, boundAt}` |
| `meta:{code}` | `{rev, clearedAt, updatedAt}` |
| `cmd:{code}:{id}` | `{id, op, args, danger, at}` —— **一条指令一个键** |
| `state:{code}` | 最近一次 ack 的 `state` + `ackAt` |

### 为什么指令要一条一个键

v1 把待执行指令放在 `cfg:{code}.cmds` 数组里，下发是「读数组 → push → 写回」。
**多个子女同时点按钮时会丢指令**：两边都读到 `[A]`，各自写回 `[A,B]` 和 `[A,C]`，
后写的覆盖先写的。Workers 的 KV 是最终一致的，这个窗口比想象中大。

现在每条指令写自己的键，彼此不覆盖，写操作天然并发安全。
代价是「取全部待执行指令」从一次 `get` 变成一次 `list` + N 次 `get`——
队列长度基本是 0~3，完全无所谓。

`meta.clearedAt` 是「清空」的兜底：清空时删所有 `cmd:` 键并记下时间，
`at <= clearedAt` 的残留指令一律视为已作废。

> **从 v1 升级**：如果你已经部署过 v1，旧的 `cfg:{code}` 键不会再被读取。
> 里面的待执行指令会丢（本来就是临时数据，重发一次即可），`bind:` 和 `state:` 不受影响，
> 长辈手机**不需要重新绑定**。想清干净就把 `cfg:` 开头的键删掉。

Workers 用 KV（**注意最终一致性**，写完立刻读可能读到旧值；对本场景够用，别拿它做计数器）。
Node 版用单个 `data/store.json`，`fs.writeFileSync` + 原子替换（写 `store.json.tmp` 再 `rename`）。

## 10. 同步时机

长辈端**不新增任何保活机制**，搭现成的车：

1. `AliveAlarmReceiver` 的 1 小时闹钟 → 顺带 `sync()`
2. 打开 `RemoteActivity` 手动「立即同步」
3. 绑定成功后立刻同步一次

**为什么不单独排一个闹钟**：多一个 AlarmManager 就多一份电和一份被 ROM 干掉的机会。
「还在吗」本来就要每小时醒一次，搭车最省。

⚠️ 所以 `AliveCenter.schedule()` 的开启条件是 **「还在吗」或「已绑定远程」任一成立**，
不是只看「还在吗」。只判后者的话，用户绑了远程却没开「还在吗」，同步永远不会跑——
表现为「绑成功了但怎么改都没反应」，很难排查。同理，关掉「还在吗」时也不能直接
`AliveCenter.cancel()`，要走 `schedule()` 按新条件重判。

## 11. 版本演进

- 请求/响应新增字段必须可选，老客户端忽略未知字段。
- 未知 `op` 一律拒绝，不做兼容猜测。
- 破坏性变更改路径（`/b2/`）而不是改语义。

### v1.1（2026-10-26）

- 存储形态：`cfg:{code}.cmds` 数组 → 每条指令一个 `cmd:{code}:{id}` 键，
  新增 `meta:{code}`。**修掉多子女同时下发时丢指令的问题。**
- `rev` 从「12」这种小序号改成 `秒级时间戳 - 1600000000`，多写者也不会撞回旧值；
  同时保证落进 32 位整数（长辈端 `optInt`）。
- `cmds` 语义明确为「全部未回执指令」，客户端按 `id` 去重。
- 管理端 `admin.html` 增加浏览器本地设备清单，一个子女可以管多台长辈手机。
- **路径和行为不变**，长辈端只多了一层「回执队列里的 id 不重复执行」的兜底。

## 12. 两套实现的分工

| | Workers | Node（NAS） |
|---|---|---|
| 部署 | `wrangler deploy`，分钟级 | `node server.js` + `cloudflared tunnel` |
| 存储 | KV（免费额度够用） | 本地 JSON 文件 |
| 可达性 | 云厂商保证 | 依赖家里电和网 |
| 数据位置 | Cloudflare | 自己家 |
| 适合 | 默认形态 | 想自己攥着数据、家里有常开设备 |

**同一套协议，`admin.html` 也是同一份**。
